Guide · Worktrees

Set up a clone or worktree without .env

A fresh clone or a new git worktree has no .env, because the file was never committed. Copying it from another folder spreads your keys one folder further.

By Zach ShallbetterPublished 14 November 2026Needs the command-line tool

On this page

  • Why the file is missing
  • Set up the new checkout
  • Let an agent work in the worktree
  • What this doesn't do

In shortRun pst project in the new checkout to see which project it is, then either write an env file of references with pst export shop/development --out .env.local or skip the file and start the app with pst run --env shop/development -- npm run dev.

Why the file is missing

An env file is gitignored, so it stays in the folder where you made it. git worktree add and git clone give you the tracked files only. The usual fix is to copy the old file across, and every copy is another place a key can leak from.

Pistachio keeps a record for each environment: its variables, each pointing at a stored item or holding a plain setting such as PORT=3000. The record belongs to the project, not to a folder, so a new checkout can use it. The examples below use an example project called shop.

Set up the new checkout

  1. Ask which project this is

    Pistachio matches the checkout to a project by its Git remotes, read from git's config and never with credentials. It shows the matching project, its environments, and a suggested export command.

  2. Link the checkout if nothing matches

    This remembers the checkout's origin as project shop and asks you first. Use --remote R to name another remote. After that, a clone in any folder resolves to shop, and an import from it names items after the project rather than the folder.

  3. Write an env file of references

    The file holds pistachio:// references and plain settings, sorted by name, and no values. If the file already exists, it is left alone and the variables that would change are named. Merge into an existing .env file covers that case.

  4. Or run without a file

    --env sets the environment's variables from its record when the command starts. Nothing is written to the folder. Without a record for that environment, it loads what the older lookup finds and says so.

Let an agent work in the worktree

If a coding agent works in the new worktree, a grant for the main repository's folder covers it. Grants cover the folder, the folders inside it and that repository's worktrees.

The grant asks once, lasts two hours here; --for always makes one that lasts until you revoke it. See Give coding agents API keys safely.

What this doesn't do

  • A project match only names the project. It never releases a value or widens a grant.
  • A match through a remote other than origin, as a fork has, is flagged and never taken as the project.
  • Values are still released only after approval, unless an item is agent-safe or a grant covers it.
  • A file written without --values holds references, not values, so it needs Pistachio to fill them in when a command starts.
  • If an environment has no record yet, pst env migrate builds one from what Pistachio already knows. Variables found through old file locations stay unconfirmed until you run pst env confirm.
