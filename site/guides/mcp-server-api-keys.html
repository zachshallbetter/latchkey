Guide · MCP servers

Keep API keys out of MCP server configs

MCP clients start servers from a JSON config, and the usual way to give a server its key is to type the key into that file. Pistachio lets the config hold a reference instead.

By Zach ShallbetterPublished 14 November 2026Needs the command-line tool

On this page

  • Why the config is a problem
  • Wrap the server
  • Pistachio's own MCP server
  • What this doesn't do

In shortSave the key in Pistachio, then change the server's command to latchkey run --no-masking -- … and put latchkey://NAME in its env. The client starts the server as before; Pistachio fills the key in for that process.

Why the config is a problem

A config such as .mcp.json or Claude Desktop's settings file holds every server's keys in plain text. It gets shared to set up a teammate, checked into a repository for a project's tools, or synced between Macs, and every key in it goes along.

Wrap the server

  1. Save the key in Pistachio

    The value is read from a hidden prompt or standard input, so it never appears in your shell history.

  2. Start the server through latchkey run

    --no-masking matters here: MCP speaks over standard output, which must pass through untouched.

  3. Decide how it may read the key

    The server is started by your agent, so its reads come from the agent's process chain. Either mark the item agent-safe, or grant it for the time you'll be working; otherwise each start asks you.

Pistachio's own MCP server

For clients without a shell, Pistachio's server offers status, listing, checking, running commands with references filled in, and asking you for a grant. It has no tool that reads a value, and the output it returns is masked.

What this doesn't do

Only servers started as a command can be wrapped. A server reached over HTTP with a header key can't get it this way. And like any command, a wrapped server holds the key in memory once it starts.
