A native Mac tool for developers

Your projects move. Your secrets don't.

Latchkey keeps development credentials in your Mac's iCloud Keychain and reconnects them to the projects that need them. Restore an environment on another Mac, run commands with the right values, and let coding agents work through access you control.

How it works

From scattered .env files to a working project.

Import the environment you already have. Latchkey stores the credentials and replaces their values with references. On another Mac, restore the project\'s environment and get back to work. The environment travels with the project; the credential stays in your vault.

1

References in your files. Values in Keychain.

Point Latchkey at an env file. A dry run shows where each value would go and sends nothing. Then one approval saves them to iCloud Keychain under the repository's name and the environment the file name implies, and --rewrite leaves a reference where each value was. Plain settings such as PORT can stay as they are with --skip.

2

Bring your environment with you.

Project environment records sync with your credentials across your Macs. A fresh checkout or worktree shouldn't mean rebuilding your environment by hand: lk project recognizes the checkout from its Git remote, and lk export writes its env file from the record, with references and plain settings, never a value, and without relying on the original machine's file paths.

3

Your credentials aren't tied to one Mac.

Items, their history and each environment's record are keychain items in Latchkey's own access group, carried end to end encrypted by iCloud Keychain to every Mac signed in to your Apple Account with Latchkey installed. On the next Mac, clone and export, and the same environment is there. Grants stay on the Mac where you made them.

Second-Mac test pending Keychain sync is Apple's; we haven't yet run this whole sequence on a second Mac for the release.

4

Let agents work. Keep control of access.

Agents can check what a task needs, run commands through Latchkey, and ask for access when a grant doesn't cover it. Set grants for a folder, a session, a command or a time limit. Review activity, and revoke the grant when the work is done. A request the grant doesn't cover, like production, asks again.

Be the person at the Mac

An agent's command is asking for two keys. Choose in the panel the way you would in the app: Deny prints the real refusal, Allow Once runs the tests with the values concealed, and a grant shows the next run going through, or, limited to one command, asking again.

You're the person at the Mac: when the agent's command asks, choose in the panel.

Everything the panel shows comes from macOS, not from the request: the program and those that started it, the folder it runs in, and its full command line. A script that talks to Latchkey directly instead of through the signed lk tool is named by its path, with a warning. The same limits can be set ahead of time with lk grant 'shop/development/*' --session --for 4h.

After an agent session

When a key changes, the reference doesn't.

lk touched lists every key Latchkey released to programs an agent started. lk rotate walks through them: it ends the grants that cover them, opens each service's page for a new key, and saves what you paste, with the old value kept in history. Every file and environment that refers to the item keeps working; with --push, linked Vercel, GitHub Actions, Railway and Fly environments get the new value too.

Mediated use

Keep supported API keys out of agent processes

For OpenAI and Anthropic, Latchkey's local proxy keeps the upstream key out of the command while forwarding its API requests. The process can still use the provider; it never receives the original key. Try what a command could do with it:

In the command's environment

OPENAI_API_KEY=lk-proxy-3f9c…8e4a
OPENAI_BASE_URL=http://127.0.0.1:52817/v1
lk run

Arriving at api.openai.com

POST /v1/chat/completions
Authorization: Bearer lk-proxy-3f9c…8e4a
Choose something for the command to try.

The command gets a placeholder and a base URL on your Mac; Latchkey adds the real key to requests bound for api.openai.com or api.anthropic.com and refuses unauthenticated ones. Other credentials are still delivered normally. For AWS, lk run --aws-session gives the command STS credentials that expire after 15 minutes, while your long-lived key stays in Latchkey.

Security

What it protects, and where it stops

Values live in iCloud Keychain in an access group only the signed Latchkey app can read. The lk tool checks the app's signature before sending anything, the app reads each caller's identity from the kernel, and every release, change and refusal goes in a tamper-evident log. Latchkey is as precise about its limits.

A released value is out of its handsA command you allowed has the key, and Latchkey can't control what it does with it. --proxy is the exception, for OpenAI and Anthropic.
A reference isn't permissionIt names a secret; it doesn't grant access to it. Every read that isn't agent-safe or granted still asks.
Anything running as you can askKeep grants narrow and short, and deny requests you don't recognize.
